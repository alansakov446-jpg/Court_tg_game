# 🏛 Telegram-бот «Суд»

Многопользовательский вымышленный судебный процесс: aiogram 3, SQLAlchemy 2 async,
PostgreSQL / Neon, Gemini. Python **3.12**. Рекомендуемый транспорт — долгоживущий
сервис в Docker (VPS/Render/Fly/Railway); GitHub Actions работает как запасной
поллер и как CI. Игра живёт на секундных таймерах, поэтому «зелёный запуск» здесь
означает только одно: за окно был реальный опрос Telegram (см. таблицу статусов ниже).

## Быстрый запуск

1. Создайте бота у **@BotFather**, получите токен. Отключите **Group Privacy** через
   `/setprivacy`, затем заново добавьте бота в группу. Иначе бот не увидит обычные
   выступления, нарушения очередности и активность игроков. Разрешите отправку сообщений.
2. Создайте PostgreSQL в Neon. Используйте **direct connection**, не адрес с `-pooler`:
   процесс удерживает session-level advisory lock, несовместимый с transaction pooling.
3. Установите зависимости и задайте переменные **в окружении**:

   ```bash
   python3.12 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt

   export BOT_TOKEN='токен от BotFather'
   export DATABASE_URL='postgresql+asyncpg://user:password@host/dbname?ssl=require'
   export GEMINI_API='key1,key2,key3,key4,key5'

   alembic upgrade head
   python main.py
   ```

   Не добавляйте реальные ключи в файлы репозитория, историю команд общего компьютера
   или логи. Приложение читает `os.getenv`/окружение; `.env` автоматически **не загружается**.
   При необходимости экспортируйте его безопасным способом перед запуском.
   URL из Neon с `postgresql://`, `sslmode=require` и `channel_binding=require` также
   нормализуется приложением: `sslmode` превращается в `ssl`, а `channel_binding` (его
   asyncpg не принимает и падает с `TypeError`) отбрасывается автоматически. SSL не отключайте.
4. В группе: `/game`, затем **каждый игрок, включая создателя**, нажимает «Вступить»
   и запускает бота в ЛС. Без этого Telegram запрещает боту первым присылать личные роли.

`RUN_SECONDS=0` (по умолчанию) — непрерывный polling; положительное значение ограничивает
сеанс для локальной отладки. `OFFSET_FILE` — путь запасного файла offset (по умолчанию
`.offset`): источник истины — строка `telegram_offset` таблицы `bot_state` в БД
(алебмик-ревизия `0002`), файл и кэш Actions используются только как fallback.
`HEALTH_FILE` (по умолчанию `health.json`) — файл живости, который поллер перезаписывает
после каждого цикла опроса. `HEALTHZ_PORT` (по умолчанию выключен) — включает встроенный
`GET /healthz` прямо в поллере.

### Честный красный и коды выхода

Поллер считает завершённые циклы `get_updates` (`poll_cycles`), увиденные и обработанные
апдейты, пишет `health.json` после каждого цикла и завершается ненулевым кодом, если окно
не дало реального поллинга:

| Код | Причина |
|---|---|
| `0` | Окно завершилось, был хотя бы один цикл `get_updates` |
| `1` | Сбой: `get_me()` не прошёл, потеряна lock-сессия БД, 0 циклов за окно, конфликт токена |
| `3` | Занят advisory lock: уже работает другой поллер (сервис или параллельное окно) |

Строка `Health polls=… updates=… handled=… offset=… lag=… lock=…` в логе — итоговая
сводка окна. Три подряд окна, в которых на старте был накопленный лаг, но ничего не
обработано, пишут ERROR `Bot looks dead` — счётчик хранится в `bot_state.silent_lag_streak`.

## Непрерывный сервис (рекомендуемый транспорт)

Игра живёт на дедлайнах 30–150 секунд, поэтому правильный транспорт — один постоянно
работающий процесс (`RUN_SECONDS=0`), а не периодические окна. **SLA в этом режиме:
ответ бота ≤ 15 секунд, круглосуточно**; `restart: always` + healthcheck поднимают его
без участия человека. Запуск в один шаг:

```bash
export BOT_TOKEN='токен от BotFather'
export DATABASE_URL='postgresql+asyncpg://user:password@host/dbname?ssl=require'  # прямой, не -pooler
export GEMINI_API='key1,key2,...'
docker compose up -d --build
```

`Dockerfile` сам выполняет `alembic upgrade head` и стартует поллер; `HEALTHCHECK`
каждые 30 секунд вызывает `python scripts/healthz.py --check` — живой считается только
процесс, чей `health.json` свежий (не старше `HEALTHZ_MAX_AGE_SECONDS`, по умолчанию 120 с)
и описывает владельца lock с хотя бы начатым поллингом. Зависший процесс перезапускается
по политике `restart: always`.

| Платформа | Как запускать |
|---|---|
| Свой VPS | `docker compose up -d` (файл `docker-compose.yml`); проброс `127.0.0.1:8080` — для локальных проб `curl http://127.0.0.1:8080/healthz` |
| Fly.io | `fly.toml` уже настроен (порт 8080, проверка `GET /healthz` каждые 30 с, автостоп выключен); секреты — `fly secrets set BOT_TOKEN=... DATABASE_URL=... GEMINI_API=...` |
| Railway | Новый сервис из этого репозитория: Dockerfile подхватывается автоматически; переменные `BOT_TOKEN`, `DATABASE_URL`, `GEMINI_API` |
| Render | `render.yaml`: worker на Docker; переменные задаются в дашборде |

В сервисном режиме `main.py` при `HEALTHZ_PORT > 0` дополнительно отвечает на
`GET /healthz` прямо из процесса поллера (200 жив / 503 мёртв) — его и проверяют
Fly/Render/Railway. Отдельный процесс `python scripts/healthz.py` отдаёт тот же
эндпоинт, если платформе нужен внешний пробник.

## GitHub Actions: запасной поллер и CI

В **Settings → Secrets and variables → Actions → Repository secrets** добавьте:

| Секрет | Значение |
|---|---|
| `BOT_TOKEN` | токен от @BotFather |
| `DATABASE_URL` | direct URL Neon с SSL, не адрес с `-pooler` |
| `GEMINI_API` | ключ Gemini или несколько ключей через запятую |

Workflow `.github/workflows/bot.yml` запускается при push в `main`, вручную через
**Actions → Court bot → Run workflow** и по расписанию каждые 5 минут. Каждый запуск
опрашивает Telegram до **600 секунд** (`timeout-minutes: 12`), после чего шаг-валидатор
проверяет `health.json`: окно без единого завершённого цикла `get_updates` делает запуск
красным. Юнит-тесты из окна убраны (они живут в `tests.yml`), чтобы расписание тратило
минуты на поллинг. В сводке запуска появляется блок **Poller health**: бот, счётчики
циклов и апдейтов, окно в UTC, `lock`, `offset` с источником, `pending_lag` и `start_lag`.

**Честно о доступности в режиме только Actions:** расписание срабатывает только для
ветки по умолчанию, планировщик GitHub задерживает его непредсказуемо (замерено
09.10.2026: интервалы 3 ч 24 м / 7 ч 28 м / 6 ч 34 м при cron `*/5`), а между окнами
`getUpdates` не вызывается вовсе. Партия на секундных таймерах в таких паузах умирает.
Этот режим годится для проверки связи и диагностики, но не для живой игры.

### Что означает статус запуска

| Статус | Что означает |
|---|---|
| ✅ зелёный + блок **Poller health** со счётчиками | За окно был реальный поллинг: `poll_cycles ≥ 1`, апдейты обработаны, `offset` сохранён в БД |
| ❌ красный, шаг `Validate polling health`, `poll_cycles=0` | Окно прошло без единого цикла опроса (например, Telegram был недоступен всё окно) |
| ❌ красный, `poll.log is empty` | Поллер не вывел ни строки (падение до старта) |
| ❌ красный, `health.json was never written` | Процесс умер до блока живости |
| ❌ красный, код 3, `Another worker is active` | Advisory lock занят другим поллером. Если развёрнут сервис — **выключите этот workflow** (Settings → Actions → General → Disable workflow), иначе каждый запуск будет честно красным |
| ❌ красный, `Another Telegram poller is using BOT_TOKEN` | Конфликт: кто-то ещё поллит этим токеном вне этого репозитория |
| ❌ красный, `Database lock connection was lost` | Потеряна сессия БД, удерживающая advisory lock |

Для ручной проверки отправьте боту `/start`, пока запуск **In progress**: в логах шага
`Poll Telegram updates` должна появиться строка `Polling started as @... (600s limit)`,
а в сводке — заполненный блок **Poller health**. В группе для обычных сообщений нужно
отключить Group Privacy у @BotFather и заново добавить бота.

Не запускайте второй poller с тем же токеном: один владелец гарантирован — `concurrency:
court-telegram-poller` сериализует запуски в Actions, а `pg_try_advisory_lock(742190018)`
не пускает второго в БД (такой запуск честно падает с кодом 3). Игры и таймеры хранятся
в PostgreSQL, `offset` — в таблице `bot_state`; кэш Actions лишь подстраховывает файл.

## Правила и принятые решения

- Базовый состав: судья, прокурор, адвокат, подсудимый, **два свидетеля и три присяжных**.
  Роли случайны; при нехватке людей — боты, при избытке — дополнительные свидетели.
  Число живых игроков кодом не ограничено, но контекст Gemini и лимиты Telegram конечны.
- Фазы: преступление 60 с → обвинение 150 с → защита 150 с → прения 150 с →
  финальное слово 60 с → вердикт 150 с. Вместе с лобби — около 15 минут без задержек.
  В прениях слово можно передавать между сторонами. Свидетель выступает в пределах времени стороны.
- 30 секунд молчания активного оратора — предупреждение; ещё 30 — нарушение и передача
  слова / завершение выступления. Повторное нарушение ведёт к отстранению. Судья в фазах
  ознакомления и голосования не считается молчащим оратором. Подсудимого отвести нельзя.
- Реплики вне очереди: штраф стороне 10$, повтор — отстранение. У нейтральных ролей нет
  кошелька: штраф дисциплинарный, учитывается в счётчике нарушений. Сообщения не удаляются;
  для механики бот должен их получать (см. Group Privacy).
- Отвод поддерживает **строгое большинство действующих живых игроков, кроме цели**.
  Автор тоже считается; себя, подсудимого и уже играющего бота отвести нельзя. Роли истца
  в этом уголовном процессе нет. Бот наследует роль, доступ к её данным и историю выступлений.
  Первое отстранение обратимо, второе — навсегда. Добровольный выход сразу окончательный.
- «Невиновный при отводе» здесь означает участника **без зафиксированных нарушений**, а не
  невиновного подсудимого. В конце игры инициатор такого отвода платит 15$ своей стороны
  (или получает дисциплинарный штраф, если роль нейтральная). Это явно выбранное правило
  для неоднозначного пункта ТЗ. Голосование и инициатор сохраняются в `games.state`.
- Корректность протеста оценивает ИИ по процессуальным критериям, независимо от решения
  судьи. Три расхождения увеличивают дисциплинарный счётчик и дают основание для отвода.
  Если оценщик недоступен, решение судьи не оценивается. Это игровая оценка, не юридическая истина.
- Присяжных минимум три: они всегда образуют фракцию. Единогласие против судьи даёт ему
  30 секунд на пересмотр. Если он не пересмотрел, сохраняется его решение. Если решения судьи
  нет к дедлайну, используется большинство поданных голосов; ничья или отсутствие голосов —
  оправдание. `/say anon` скрывает имя от судьи, но не гарантирует анонимность от администратора БД.
- Стартовый бюджет **50$ на сторону в партии**, экспертиза 25$. В прениях ведущий может
  назначить цену 10–120$. Победа по вынесенному вердикту даёт +100$; это итог этой партии,
  не накопительный профиль между играми. Скрытая `truth` не передаётся ботам и не определяет
  автоматически судебный вердикт. Экспертизы возвращают заранее созданную трактовку улики,
  а не заново выдумывают факты.
- Дело содержит 5–7 улик. В прениях неопубликованные факты становятся публичными;
  трактовки остаются скрытыми до экспертизы. Генератор заполняет личные сведения каждой роли.
- Боты выступают, отвечают на допрос, дают финальное слово, голосуют и выносят вердикт.
  Боты сторон также выбирают экспертизу, вызов свидетеля или протест (не больше одного
  дополнительного действия на роль/фазу). Бот-судья разрешает протесты; переходами по дедлайнам
  управляет движок. Отводы и личную переписку присяжных инициируют люди, не автономный планировщик.

## ИИ, приватность и отказоустойчивость

`gemini-3.8-flash` → `gemini-3.5-flash-lite`; до пяти ключей в каждой модели. Провайдер
может отзывать старые имена моделей (HTTP 404 `NOT_FOUND` на все ключи — именно так в
октябре 2026 были отключены `gemini-2.5-*`); актуальность каскада проверяется пробой
`scripts/ai_probe.py`. Часть моделей отклоняет `thinkingBudget: 0`
(HTTP 400 `INVALID_ARGUMENT` — так ведёт себя `gemini-3.5-flash-lite`): каскад повторяет
запрос без `thinkingConfig`, запоминает это за моделью и больше не спорит с ней. После HTTP 429
пара **ключ + модель** получает cooldown 60 секунд в памяти. Следующий ключ пробуется сразу;
при исчерпании модели начинается следующая. Если же модель отвечает ошибкой сервера (5xx),
зависает по таймауту или недостижима по сети — cooldown получает **сразу вся модель**
(все её ключи), чтобы каскад сразу перешёл к следующей и уложился в бюджет генерации.
Lite имеет отдельную квоту. Перезапуск очищает
cooldown. Сетевые ошибки, невалидный JSON, пустые ответы и ошибки API пробуют следующий вариант.
Ключ передаётся заголовком, не URL; тексты ответов провайдера и ключи не логируются.

Если новое дело не удалось создать ни по одной из причин (модель недоступна, квоты,
сетевая ошибка, некорректные черновики ИИ, повтор уже известного дела), зал **стартует
сразу** на детерминированном шаблоне дела из `game/rules.py` (`fallback_case`): описание
уникально для каждой партии, скрытое решение и улики зашиты в коде. Игрокам сообщается
конкретная причина отказа ИИ простыми словами (`explain_failure`), а в лог уходит полная
техническая сводка. Игра не стартует с пустым делом. Если ИИ недоступен уже во время игры,
бот использует нейтральную реплику, голосует за недоказанность, пропускает необязательные
действия; фазы продолжаются.

### Диагностика ИИ в логах

Отказ ИИ **не** делает запуск workflow красным: зал живёт дальше, поэтому причина пишется в лог.
Логгеры: `court.ai` (каскад Gemini), `court.ai.host` (проверка черновиков дела),
`court.game` (последствия для конкретной игры).

Каждая неудачная попытка — одна строка WARNING: модель, индекс ключа (`key=#0`, не сам ключ),
HTTP-статус и код ошибки провайдера (`http=429 body_not_json cooldown=60s`,
`http=400 INVALID_ARGUMENT message='API key not valid: [redacted]'`), класс таймаута
(`timeout=ReadTimeout limit=30s`), сетевая ошибка (`network=ConnectError`), причина
непригодного ответа (`blocked=SAFETY`, `no_parts finish=MAX_TOKENS`, `empty_text`) или ошибка
валидации JSON (`invalid_json=JSONDecodeError answer_chars=8`). HTTP 429 пишется уровнем INFO,
потому что каскад продолжается другим ключом.

Исчерпание каскада — одна строка ERROR `Gemini exhausted ... cause=<сводка>`, где повторы
схлопнуты (`http=429 x10`) и ограничены 600 символами; та же сводка передаётся в
`AIUnavailable.summary`. Отдельно логируются: `Case draft rejected attempt=1/3 ... reason=Нужно 5–7 улик`
(причины локальные, из `validate_case`), `New case was not created game=7 players=3 reason=...; retry in 60s`,
а при успехе — `Case created game=7 evidence=6 roles=9`.

В лог **не** попадают: API-ключ (он ещё и вырезается из сообщения провайдера), тело запроса,
промпт (только `prompt_chars`), тексты ответов и сгенерированное дело, имена игроков,
содержимое чата и `truth`.

Порядок строк при создании дела: `Lobby opened game=7 requested_bots=2 case_due_in=150s`
(команда `/game` только открывает зал на 2:30, генерация начинается по дедлайну или сразу
после `/startnow`) → `Case draft accepted attempt=1/3` или `Case draft rejected ...` →
`Case created game=7 evidence=6 roles=9`. Если последней строки нет, а `New case was not created`
есть — дело не создано, причина указана в `reason=`.

Workflow `.github/workflows/bot.yml` пишет вывод поллера в `poll.log` (игнорируется git),
загружает его артефактом `poller-log-<run>-<attempt>` и добавляет в сводку запуска блок
**AI diagnostics** со всеми строками WARNING/ERROR от `court.ai`/`court.game`. Пустой блок
означает, что за окно опроса сбоев ИИ не было.

Workflow `.github/workflows/diagnostics.yml` (запуск вручную или push в feature-ветку)
прогоняет `scripts/ai_probe.py` против реального `GEMINI_API`, добавляет санитизированные
фрагменты из последних запусков Court bot и публикует отчёт: коммитом в feature-ветку и
check-run «AI probe report». Ключи, промпты, ответы, тексты дел и `truth` в отчёт не попадают.

Нормализованный SHA-256 описания уникален в БД: **точные повторы отвергаются**. Последние
100 сюжетов передаются генератору с запретом смысловых повторов. Это не строгая гарантия
семантической уникальности всех возможных преступлений; для неё нужна дополнительная проверка.

У `evidence` и `statements` поле `visible_to_roles TEXT[]`. `public` — общие сведения.
Запрос контекста использует PostgreSQL `&& ARRAY['public', role]`, а не чтение всех записей
с фильтрацией в Python. Интерпретации не включаются в контекст до публикации экспертизы.
Личные сообщения присяжных видны только ролям отправителя/получателя. Бот роли не получает
`games.state`, `truth` или чужие личные факты. Все доступные сохранённые реплики включаются
в память — длинные партии могут превысить окно модели, тогда используется fallback.

Ведущий, напротив, создаёт всё дело и его скрытое решение. Ролевой бот знает не «всё дело»,
а ровно то, что знала его роль плюс публичный чат. Не отправляйте реальные персональные
или юридические сведения: доступный игровой контекст передаётся Google Gemini. Промпты
отделяют цитаты от инструкций, но абсолютной защиты от prompt injection и галлюцинаций нет.

## Структура и проверки

```text
main.py                 polling → транзакция апдейта → offset (bot_state) → игровые тики;
                        счётчики живости, health.json, коды выхода 0/1/3
ai/gemini.py            каскад, cooldown и безопасная диагностика отказов
ai/host.py              генерация дела, речь, выбор действия
game/                   правила, команды, лобби, фазы, экономика
db/models.py            games, players, roles, evidence, statements, economy, bot_state
alembic/                версионируемая схема, уникальный индекс открытого зала,
                        0002 — таблица bot_state для offset
scripts/ai_probe.py     живая проба генерации дела: пишет санитизированный отчёт
scripts/healthz.py      зонд живости: --check для HEALTHCHECK и GET /healthz
Dockerfile, *.yml/toml  сервисный деплой: compose (VPS), fly.toml, render.yaml
.github/workflows/      bot.yml — запасной поллер с валидатором и блоком здоровья;
                        diagnostics.yml — проба ИИ + фрагменты логов Court bot;
                        tests.yml — CI на PostgreSQL 16
```

```bash
python -m unittest discover -s tests -v
python -m compileall -q ai db game main.py alembic
alembic upgrade head --sql  # проверить SQL без подключения к БД
```

Unit-тесты не используют ключи и сеть: каскад HTTP замокан. Интеграционные тесты включаются
через `TEST_DATABASE_URL` и проверяют реальные PostgreSQL ARRAY, JSONB, сохранение игры,
замен и результатов после открытия новой сессии. **Они очищают все игровые таблицы!**
Используйте только отдельную одноразовую тестовую БД:

```bash
export TEST_DATABASE_URL='postgresql+asyncpg://user:password@localhost/court_test'
DATABASE_URL="$TEST_DATABASE_URL" alembic upgrade head
python -m unittest discover -s tests -v
```

CI делает это на отдельном PostgreSQL-сервисе, проверяет соответствие миграции моделям
через `alembic check` и обратную миграцию. Боевые секреты ему не нужны.

Перед запуском для игроков проверьте на тестовой группе вступление через ЛС, получение
обычных сообщений, `/game 9`, `/startnow`, `/expert`, отвод, финальное слово, голосование,
перезапуск процесса и восстановление offset. Живые Telegram, Neon и Gemini требуют ваших
секретов и сетевого доступа; unit-тесты не заменяют этот smoke-тест.
